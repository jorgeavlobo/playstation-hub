## 1. Key findings

1. The old implementation is a Home Assistant App/add-on process depending on PS5-MQTT and Mosquitto, with independent SQLite history and a separate Lovelace card. It is not a native Home Assistant integration Config Entry. Old options live in Supervisor-managed /data/options.json; backend/config.yaml declares slug ps5_monitor, version 0.5.0, manual startup, aarch64 and template DB path /data/ps5_monitor.db. This is a source template, not confirmation of the installed path.
2. backend/app/database.py defines schema version 3: schema_version, events, sessions, checkpoints and monitoring_state. Opening Database(path) creates its parent directory and connects with SQLite creation permitted, then runs migration to the latest schema. NEVER use this constructor on the original live or archived file during a read-only migration inventory.
3. **No canonical physical PS5 ID is stored in the reviewed legacy table definitions.** The single App config contains mqtt_topic and player_name; these are configuration/source selection labels, not verified immutable hardware/account identities. Historical rows cannot be safely attached to any new PS5 Config Entry by IP, name or MQTT topic alone.
4. Legacy sessions represent console or gaming usage, with UTC Unix REAL start/end, optional player and title metadata; open sessions are bounded by checkpoints. The database stores sparse state-change events, not all accepted heartbeat observations. Imported sessions can be preserved as historical source evidence, but event gaps must not be interpreted as continuous direct PlayStation observations.
5. Effective runtime continuity limit is 30 seconds in main.py (SessionTracker called with max_gap_seconds=30.0), though helper defaults use 90 seconds. Do not recalculate legacy durations with the future native policy or fill 31-second unknown gaps. Retain the old policy version and the originally committed interval boundaries.
6. Stats are computed from half-open UTC sessions with Europe/Lisbon report calendar and DST. A 36-month index and 12-month published summary are UI windows, NOT a proven data-retention limit; no automatic 36-month row deletion exists in the reviewed code.
7. Old MQTT publisher generates TEN retained single-component Discovery sensors with unique ID pattern ps5_monitor_<key>, synthetic device identifier ps5_monitoring_service and discovery topics homeassistant/sensor/ps5_monitoring_service/<key>/config. The old card hardcodes sensor.ps5_monitoring_service_ps5_ entity prefix. Real Home Assistant entity IDs may have been user-renamed, so this code is not proof of current registry IDs.
8. MQTT broker retains discovery configurations, and official Home Assistant documentation confirms they can recreate entities after the old App stops. Cleanup needs a separately verified and consented inventory of the old monitor's EXACT topics; do not indiscriminately delete PS5-MQTT devices, sensors or switch controls. PS5-MQTT entities such as a PlayStation activity sensor or power switch are NOT generated by the old monitor publisher.
9. The frontend history and daily request clients use HA's authenticated WebSocket AS A MQTT transport, including mqtt/subscribe and mqtt.publish. The new native sidebar should reuse request-correlation, calendar-navigation and historical UX principles while replacing MQTT topics with native playstation_hub backend API. Do not port the old Lovelace card as a duplicate permanent UI.
10. Legacy source includes backend/frontend unit-test files and README historical notes. This audit RAN NO TESTS. Legacy README says earlier frontend tests passed and notes a backend history-worker issue; these source statements cannot certify current behavior or successful migration.

## 3. Exact legacy SQLite schema (v3)

### schema_version
Version INTEGER NOT NULL. v1 creates events/sessions, v2 checkpoints, v3 monitoring_state. Constructor migrates by default; migration importer MUST query in read-only existing-file mode and inspect schema before any write.

### events
id INTEGER PRIMARY KEY AUTOINCREMENT; event_type TEXT NOT NULL; occurred_at REAL NOT NULL; payload_json TEXT optional. Index on occurred_at. EventType values: state_update, connection_lost, connection_restored, service_started, service_stopped. State_update is written when power/activity/player/title state changes, not each heartbeat. Event payload can contain private player/title information and is audit evidence, not a complete source-observation stream.

### sessions
id INTEGER PRIMARY KEY AUTOINCREMENT; session_type TEXT constrained to console/gaming; started_at REAL; ended_at REAL nullable; player_name, title_id, title_name, title_image optional. Check constraints require ended_at >= started_at and gaming player_name present. Partial unique index permits one open console globally and one open gaming session per player_name. There is NO console hardware UUID, canonical PSN account key, source run UUID or target ledger lineage field in these columns.

### checkpoints
session_id INTEGER PRIMARY KEY; observed_at REAL; updated_at REAL; FK to sessions(id) with ON DELETE CASCADE. An open session with a valid checkpoint is bounded at observed_at; without one, at started_at. Reject inconsistent checkpoints and foreign keys, don't silently mutate original DB.

### monitoring_state
Singleton id=1 with last_observation_at, last_power, last_activity, last_player (serialized JSON), last_title_id and updated_at. v3 may initialize from latest sparse state_update. This is legacy last-known state, not a fresh native console observation or physical identity.

## 4. Migration classification and mapping proposal

| Source object | Proposed target representation | Confidence |
| --- | --- | --- |
| Closed console session | Archived LEGACY_UNATTRIBUTED session with exact UTC bounds and provenance | Source-row evidence, no physical ID |
| Closed gaming session | Archived LEGACY_UNATTRIBUTED with private player label and title metadata | Player label != authenticated PSN |
| Open session + checkpoint | Import derived bounded interval, preserve original null end and checkpoint separately | Last evidence only, not physical transition |
| Open session without checkpoint | Zero confirmed duration beyond start | Do not extend |
| events rows | Separate legacy audit evidence, source local row ID and payload validation | Sparse, not periodic observations |
| monitoring_state | Optional last-known diagnostic provenance | Never current state |
| options player_name | Optional private legacy display label | Not PSN authorization |
| options MQTT topic | Restricted audit only if justified | Not physical hardware proof |
| title_image | Untrusted legacy URL metadata | Never fetch automatically |
| MQTT credentials and options.json | **NEVER** import into historical ledger | Secrets |
| Retained live MQTT snapshot | Ignore as historical evidence | Ephemeral |
| 36-month index / sensor attributes | Recompute from imported validated sessions | UI cache, not source of truth |
| Lovelace old entity IDs | Proposed compatibility mapping only after live registry inventory | Not native stable identity |

**P0 mandatory:** imported data starts with physical owner=NULL / LEGACY_UNATTRIBUTED. No auto association to a newly discovered PS5, even if old one-topic config is known. The operator may supply later independent evidence and request review, but original legacy provenance never disappears and no false proof of exact hardware is manufactured. Old player names are not PSN account ID or authorization.

## 5. Non-destructive source acquisition

Only after future explicit user authorization and a scheduled maintenance/cutover phase:
1. Verify actual installed App slug, active settings and persistent /data storage location; the source template is NOT a measurement of installed data. Never dump private options/credentials to logs or repo.
2. Obtain a consistent SQLite source backup using SQLite Online Backup or a proven clean shutdown plus complete source archive. Never just copy an active main DB without its WAL/journal, nor delete hot companions. Preserve original bytes and source hash in protected private storage.
3. Stop or safely freeze old ingestion for final cutover; prevent parallel old App and native monitor from creating contradictory histories.
4. Open the COPIED legacy SQLite with non-create read-only mode. Do not instantiate legacy Database because it creates/migrates schema.
5. Verify integrity_check, foreign_key_check, schema_version in {supported versions}, fields/indices, UTC timestamps, event JSON shape, open sessions/checkpoints, player/title length and source counts.
6. Produce an admin dry-run preview: source hash, row counts, excluded/quarantined anomalies, totals by year/month/type and differences under the old Lisbon timezone and 30s continuity semantics. No target writes during preview.
7. After admin confirmation, stage a distinct target generation with a stable migration_batch_uuid, legacy_source_uuid, original table/row IDs, schema/policy version and immutable source manifest. Idempotent repeat import of same source must produce zero duplicates.
8. Validate resulting target generation and totals, promote via approved ADR-0015 pointer protocol after terminal worker proof; keep original/source and rollback export intact. New monitoring starts at a fresh evidence boundary, never backfills an overlapping gap.
9. Only after independent native monitoring validation and preserved source backups consider retirement of MQTT App/card/discovery, with rollback plan.

No migration code or real data access was performed by this research.

## 6. Old MQTT discovery and Home Assistant registry cutover

Legacy publisher topic pattern: homeassistant/sensor/ps5_monitoring_service/<key>/config, unique_id ps5_monitor_<key>, synthetic device identifier ps5_monitoring_service. Keys: console_today, console_week, console_month, gaming_today, gaming_week, gaming_month, monthly_sessions, top_game, history, game_library. This list is verified in source. The old frontend hardcodes a subset of sensor.ps5_monitoring_service_ps5_ entity names, but live entity registry IDs and user automations may differ.

Home Assistant's official MQTT integration guide says retained Discovery config can revive ghost entities after broker restart and documents targeted removal by publishing empty retained content to the exact discovery topic. That is an invasive live-broker operation and MUST NOT be done without an inventory, user authorization, saved discovery payloads, dependent automation review and verified new entity continuity. The external PS5-MQTT monitor/control topics and any power switch are a distinct third-party integration: never clear broad topic prefixes or remove its entities by mistake. Native PlayStation Hub must assign its own per-console IDs rather than claiming the old synthetic MQTT monitor device as a physical PS5.

Do not automatically alter the entity registry, automations, dashboards, MQTT broker, Lovelace resources or HACS installation during research. Decommissioning legacy services is a LATER separate work package.

## 7. Provenance and idempotency model

A future migration manifest needs: legacy_source_uuid, exported_snapshot_sha256 (integrity not authentication), source schema version, old source App version when verified, legacy record namespace, migration_batch_uuid, original_table, original_row_id, raw UTC bounds, bounded effective duration, original checkpoint, original player label, game title metadata, old report timezone, continuity policy version, confidence=LEGACY_UNATTRIBUTED, target generation and import revision.

Two exported databases may both have session id=1, so imported row uniqueness must include legacy_source_uuid and original table/row ID. An existing source re-import retries idempotently; a later snapshot of the same original database is NOT trivially another source or append-only set unless common ancestry and overlap are verified. Avoid double counts across the transition to live native monitoring. Preserve source DB and original raw records; do not rewrite event rows as if they were authenticated native LAN observations.

Rollback is a controlled administrative process: the original legacy snapshot remains immutable, newer target-ledger writes cannot be deleted by blind old-pointer rollback, and Home Assistant Config Entry state plus MQTT retained discovery are not one atomic transaction.

## 8. Risks and tests to plan

- Missing physical console UUID in legacy sessions and singleton monitoring_state.
- Old App effective 30-second gap (not 90 defaults) and checkpoint uncertainty, open sessions, sparse events.
- Old timezone Europe/Lisbon, DST and half-open calendar boundaries, 36-month index not retention.
- Schema v1/v2/v3 and unexpected newer/partial schemas, blob/JSON/UTF-8/timestamp invalids.
- Source copy consistency and security: unavailable old /data, credentials in options, hot WAL.
- Duplicate import batches, different source snapshots, old/new overlap, restarted migration and lost acknowledgement.
- MQTT retained discovery ghost entities, automation dependencies, wrong PS5-MQTT topic retirement.
- New native panel vs old Lovelace hardcoded entities; avoid claiming actual HA registry state from source.
- Current controls/PSN tokens are not migrated from historical data.

## 9. Decision and source limitations

**Source confirmed:** sanitized develop source structure and fields, App dependencies, effective 30s runtime policy, the synthetic MQTT discovery IDs, hardcoded old frontend references and existence of source test files. **Not known:** actual installed App options, current DB schema/size/rows, which console produced each record, whether a coherent source backup exists, live entities/automations and whether old tests pass today. **Proposed:** the archival LEGACY_UNATTRIBUTED import, metadata manifest, admin preview/confirm, staged generation and separate MQTT retirement.
